직트 공통 저장 모듈 — 자동 시험

저장 모듈(jikt_store.js)이 제대로 도는지 마흔아홉 가지를 스스로 돌려 봅니다.
이 시험은 실제 저장칸을 건드리지 않습니다.
시험이 시작되면 메모리에만 있는 가짜 저장칸을 저장 모듈에 끼워 넣고, 처음부터 끝까지 거기서만 돕니다. 직트의 실제 옛 이름표 다섯 개(jikt_gyeol_v1 · jikt_key_v1 · jikt_money_v1 · jikt_pull_v2 · jikt_title_v1)와 새 상자(jikt_store_v1)에는 글자 하나 쓰지 않습니다. 되돌리기 자체가 필요 없습니다.
아래 표에서 시험 전후의 실제 이름표 상태를 직접 견주어 보여 드립니다.
시험을 시작합니다…

실제 옛 이름표 다섯 개 — 시험 전후 비교 (읽기만 했습니다)

이름표같은가 길이 (전 → 후)앞 40글자 (전 → 후)
통과는 초록, 실패는 빨강입니다. 실패한 줄에는 무엇이 어떻게 달랐는지 함께 적힙니다.
시험 13번은 옛 다섯 저장칸의 칸을 하나하나 세어, 새 구조로 자리를 찾은 칸과 raw(안전망)에만 남은 칸의 합이 원본 칸 수와 같은지 확인합니다.
시험 14번은 이관이 도는 동안 옛 이름표 다섯 개에 쓰기가 한 번도 없었는지를 접근 기록으로 확인합니다.
시험 15~29번은 1차 검토에서 나온 여덟 가지 결함을 하나씩 되짚습니다 — 판번호가 다른 파일 거부(15), 지운 번호 다시 안 쓰기(16·17), 연결 충돌 막기(18~21), 칸 순서만 바뀐 자료 다시 안 옮기기(22), 저장칸이 일부만 있거나 깨졌을 때(23·24), 이관 도중 오류(25), 역할·형식(26), 모든 목록 줄의 고유 번호(27), 근거 줄 필수값(28), 깨진 저장칸 막기(29).
시험 30~40번은 2차 검토에서 나온 여덟 가지를 되짚는 반례 시험입니다 — 옛 2판 파일은 사람 확인을 요구하며 거부(30), 판번호가 다르면 읽기도 거부(31), 풀링 → 기획 항목 → KEY 영상의 한 방향 한 갈래 연결(32), 기존 새 자료를 지우지 않는 이관(33), 고유 번호가 빠지면 저장·가져오기 거부(34), v5.1 사건 목록 일곱 개(35), 다른 탭에서 깨졌을 때 저장 막힘(36), 측정일 없는 known 은 판정에 안 씀(37), 사유·작업자 공백 거부(38), 이관 다섯이 전부 실패하면 저장칸 무변경(39), 숫자가 아닌 발견 단계 거부(40).
시험 41~48번은 3차 검토에서 나온 일곱 가지를 되짚습니다 — 안쪽 고유 번호가 빠진 3판 저장칸은 읽기도 거부(41), save 에 잘못된 것을 주면 실패하고 원문이 그대로(42), 새로 시작 전 원문 백업과 백업 실패 시 중단(43), 다른 화면이 저장한 뒤 낡은 사본 저장은 충돌로 거부(44), 만들 때의 역할(created_role) 누락·잘못된 값·나중에 바꾸기 거부(45), 목록의 숫자·글자 줄과 KEY의 null 겨냥 칸과 겹치는 표시 번호 거부(46), 달력에 없는 날짜와 경계 없는 bounded 거부(47), 반례 실행기가 아무 경로에서나 c01~c12 열두 개만 실행(48 — 화면에서는 건너뜁니다).
시험 49번은 4차 검토에서 나온 한 가지입니다 — 표시 번호를 저장하는 다섯 목록 (videos · key_contents · channel.problems · reference_videos · title_candidates) 전부에 겹침·잘못된 값 검사를 건다(49).
시험 15번부터는 매번 완전히 새 메모리 저장칸을 따로 만들어 씁니다. 여기서도 실제 저장칸은 건드리지 않습니다.
